> **Status:** under review.

## Where we actually are

LawTrack AI works end to end today as a **local, single-user demo**: upload a PDF → Claude extracts
cited clauses → maps them to configuration recommendations → a human accepts/edits/rejects each one →
finalize commits the accepted set into a versioned layer config, snapshotting a `PolicyVersion` and
logging gaps as `UnsupportedCalculation` rows. The review surface (split cited view, per-finding chat,
decision record, change-set export) is real and works.

What is missing falls into four buckets, and three findings from the code shape everything below.

**1. Nothing currently measures accuracy.** `backend/pipeline/taxonomy.py:107` — `build_mapping_system()`
runs in *config-recommendation mode*: free-text `policy_field`, `capability_code` deliberately left
unset, and only `adjust`/`flag` permitted as classifications. But `backend/pipeline/eval_harness.py` and
`goldenset/golden.json` key **entirely** on `capability_code`, and `reduce_findings_to_prediction()`
silently skips any finding where it is `None`. So `eval_harness.py --run` scores empty against the live
pipeline. The eval loop and the pipeline have drifted apart, and the `match`/`gap`/`conflict`
classifications are unreachable from the live prompt even though the data model, the golden set, the
`UnsupportedCalculation` table and the Layers UI all still support them.

**2. There is no cloud configuration of any kind.** The only infrastructure artifact in the repo is
`docker-compose.yml`. No Terraform, no Cloud Build, no GitHub Actions, no Alembic. The GCP deployment
exists only as five prose steps in `README.md`. Data lives in a local SQLite file
(`backend/lawtrack.db`) despite the configured default being Postgres, and uploaded PDFs live on local
disk.

**3. The capability model is a draft markdown file that no code imports.**
`../pay-policy/pay-policy-field-catalog.md` (~40 `C` current fields, 11 `T` target fields) is precisely
the "what can the engine fulfill, and what can't it" model — but it is prose, not signed off, and
carries three named open questions of which break fields are called "the main blocker."

### Audience model

- **Stage 1 — Assaf only.** Full app, including Layers and finalize.
- **Stage 2 — many contributors: day.io staff (CS, onboarding) *and external consultants*, using the
  Documents section only.** Never Layers, never finalize. The goal of stage 2 is **input volume** —
  more documents and more human decisions — which is also the raw material the accuracy work needs.

This shapes workstream C, and it makes two things that look like polish into hard requirements: URL
routing (you cannot send someone a link to a document today) and reviewer-decision capture (the
corrections are the accuracy signal).

- **A1 (Alembic)** and **B1 (GCS)** must land before any Cloud Run deploy that keeps data.

  gates most of workstream D.

  time.

  golden set, not after.
